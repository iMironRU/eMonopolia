# Архитектура

## Высокоуровневая структура

```
┌──────────────────────────────────────────────────┐
│              data/  (single source of truth)     │
│           YAML: cards, properties, events        │
└──────────────────────────────────────────────────┘
              │              │              │
              ▼              ▼              ▼
       ┌──────────┐  ┌────────────┐  ┌──────────┐
       │ apps/web │  │  print/    │  │ apps/tma │
       │ Next.js  │  │  PDF gen   │  │  Phase 2 │
       └──────────┘  └────────────┘  └──────────┘
              │
              ▼
       ┌──────────┐
       │content/  │
       │ i18n .md │
       └──────────┘
```

## Принципы

### 1. Единый источник истины

Все игровые данные живут в `data/`. Из них генерируется:
- Веб-приложение (импорт YAML на этапе сборки)
- Печатные карточки (скрипт генерации PDF)
- Печатное поле (SVG из data/board.yaml)
- Документация (можно генерировать табличку из YAML)

**Нигде не дублировать.** Изменили цену поля — поменялось везде.

### 2. Контент отдельно от механики

| Что | Где |
|---|---|
| Цена, рента, трафик | `data/properties.yaml` |
| Имя поля | `data/properties.yaml` |
| Обучающий текст | `content/ru/properties/{id}.md` |

Это позволяет:
- Переводить контент без трогания механики
- Обновлять цифры про реальные сервисы (выручка Google) без редактирования YAML
- Делать вариативные тексты для разных редакций

### 3. Редакции — данные, не код

```
data/editions/
  national.yaml      — какие поля используются в национальной редакции
  international.yaml — какие в международной
  mixed.yaml         — какие в смешанной
```

Каждая редакция — это просто список ID полей + опционально переопределение имён.

## Технологический стек

### Phase 1 — Web

- **Next.js 14+** с App Router
- **TypeScript**
- **Tailwind CSS** для стилей (как в Megatorg)
- **YAML loader** на этапе сборки (например, `js-yaml`)
- **QR generation** — `qrcode` или серверная генерация
- **Деплой** — GitHub Pages через GitHub Actions

Почему Next.js, а не Vite + React:
- Static export (`output: 'export'`) даёт чистую статику
- Готовый роутинг (нужен для страниц карточек `/card/[id]`)
- Если потом нужен бэк — Next.js его поддерживает без переписывания

### Phase 2 — TMA

- Тот же React-код
- `@telegram-apps/sdk-react` для интеграции
- Авторизация через Telegram WebApp API
- Деплой — тот же GitHub Pages, бот в качестве лаунчера

### Phase 2/3 — API

Если потребуется (для удалённой игры):
- Node.js + Fastify или Hono
- WebSocket для синхронизации ходов
- SQLite/PostgreSQL для состояния партий
- Деплой — Railway/Fly.io или VPS

## Сборка печатных материалов

`print/` содержит:
- **Скрипты генерации** — берут данные из `data/`, генерируют SVG/PDF
- **Шаблоны** — Inkscape SVG или раскладка в HTML+Puppeteer
- **Готовые PDF** — финальные файлы для печати (генерятся CI)

Возможные подходы:
- **HTML+Puppeteer** — карточки рендерятся как HTML, экспорт в PDF
- **SVG + Inkscape CLI** — для печатного поля
- **LaTeX** — для красивых правил

## CI/CD

`.github/workflows/`:
- `web-deploy.yml` — сборка и деплой Next.js на GitHub Pages при push в main
- `data-validate.yml` — валидация YAML (`scripts/validate-data.mjs`), typecheck и сборка приложения на каждом PR
- `print.yml` — генерация PDF при изменении в `data/` или `print/`
- `release.yml` — релиз с печатными материалами при тегах
